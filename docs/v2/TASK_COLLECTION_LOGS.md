## 两端事件协议

助手独立操作开始时生成`task_run_id`，先于设备识别存在。原`upgrade_run_id`仍表示一次设备逐卡采集/升级关联，不冒充整次任务。

事件携带`task_protocol:1`、稳定任务ID、唯一`event_id`和递增`event_sequence`。事件种类是快照、接收卡关键采集节点和异常；异常来源另分automation、human、unknown。人工停止本身不产生自动异常，来源未确认的旧失败通知只留归档。

助手的`StartPrepare()`开始新任务；同一任务重试、同机多网口/多批次保持任务身份；显式开始下一设备操作产生新任务。`StructuredUpgradeLog.Matched()`及`Result()`继续复用现有逐卡比较与实际回读，`CollectionComplete()`确认所有观测到的接收卡完成，并阻止声明数量与实读数量不一致的清单获得成功资格。

新任务日志从任务起点读取，避免把全天其他任务正文冒充本任务日志。每个事件先原子落盘并刷新，再进入发送队列。重发使用完全相同的JSON，已接收凭据与原始事件文件分开保存；事件原件不因服务器接收而删除。

## 接收端实际流程

认证上传 → 校验任务协议 → 按机器与任务ID找到独立事件日志 → 检查事件ID/序号冲突 → 刷盘保存原始上传 → 按事件序号恢复任务状态 → 分别排队成功表和异常表 → 严格核对现有字段 → 按稳定任务主键查询并创建/更新 → 保存飞书行ID及本地人工编辑基线。

成功资格要求真实逐卡身份、状态和版本来源匹配；只出现“接收卡”、`done`或整批成功布尔值均不能过关。升级后字段只能使用实际同卡回读；无需升级必须有实际版本比较。一次任务所有接收卡完成后才入成功表，后续退出或跳转不撤销成功。

同一任务已有成功事实后，较晚的不完整诊断不抹掉已确认的逐卡结果。较旧序号晚到时，不覆盖较新快照，但其中新的真实异常仍保留。相同事件或序号却内容不同返回409，不覆写原件。

两表分别写入，一表同步出错不阻止另一表。成功与异常可以同时存在。不同任务不按型号、SN、机器码或日期合并。两表主键含同一个原始任务ID，机器散列用于防止跨机器碰撞。

飞书创建使用稳定UUID幂等令牌，每次重试还会先查稳定任务主键，处理远端已写入但响应丢失的情况。不同来源的人工备注字段从写入集合中排除。

领导表不再需要上传计数、原始日志、自动建议或自动写入基线列。人工编辑基线及发送前待确认基线保存到接收端本地凭据；人工修改及人工清空都会被保护。网络结果不明确时采用保守保护，可能停止更新不确定字段，不冒险覆盖人工内容。

HTTP`accepted/durable`只表示接收端原件已落盘；响应分别报告成功表/异常表`queued`、`synced`、`configuration-required`、`not-applicable`。上传失败不反向认定设备升级失败。

## 配置与交付状态

助手最新源码默认启用新协议，正常使用无需配置环境变量；`HUIDU_TASK_LOG_PROTOCOL=0`是明确关闭开关。模拟、演示、计算模式及离线测试禁止实际上传，包括关闭收尾路径。

接收端`FEISHU_TASK_PROTOCOL_ONLY=1`禁止旧包直接入成功表，旧包仅归档；不会把历史设备/日期队列自动迁移到新表。`FEISHU_TASK_SYNC_ENABLED=1`才开启新的两表同步，异常表必须使用独立多维表格。新写入器只读校验字段，不自动补建删除过的技术列。

接收端已恢复原入口及只读索引，旧同步关闭，新两表同步已开启；用户个人账号已获内部表查看权限。不迁移旧失败记录，不代替助手项目发布安装包。
