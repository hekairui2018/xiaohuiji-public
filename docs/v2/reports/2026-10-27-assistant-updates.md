# Firmware assistant update publication service

The existing receiver now exposes exact product/channel-scoped signed update queries and immutable single-EXE downloads. Publication is a local explicit operation, with x64 PE, size and SHA256 checks, staged copying, fsync, a publication lock and one atomic signed pointer switch. Identical retries are idempotent; interrupted pre-switch packages remain inaccessible and can be verified/reused. Rollback revokes the current build and promotes the retained predecessor. Development builds never enter stable automatically.

HTTP transport remains in use: the existing hostname returned an empty response during normal HTTPS/certificate verification. No certificate bypass or functioning HTTPS claim is made. A dedicated RSA-3072/PSS-SHA256 trust root signs the exact UTF-8 manifest bytes, binding product, channel, sequence, expiry, build, release information and EXE hash/size. Clients must pin the independently delivered public key, validate freshness/sequence/channel and recompute update decisions from the signed payload. Windows Authenticode was not added. The 7-day manifest lifetime requires explicit renewal; no automatic signing task was installed.

Real public-network acceptance used a newly compiled 3072-byte diagnostic-only EXE, not an assistant release. Two signed test versions were downloaded in full and checked by SHA256; current/same/newer build queries, repeat download, rollback, withdrawn-file denial and no-release responses were verified. The stable pointer stayed byte-for-byte unchanged with no package; the test channel was disabled afterwards. Existing public wiki and log authentication checks also passed. The service was switched after three idle observations with no pending sync work; original runtime configuration and watchdog were retained.

Local validation: 21 focused tests passed, including isolated missing/corrupt files, metadata mismatch, interrupted/repeated publication, lock contention, signature tampering/expiry/channel substitution, server/guard integration and maintenance waiting for existing handlers. Public-source adaptation: 17 independently runnable checks passed. The repository's deliberately sanitized empty data manifest prevents two existing full-application public-access cases from running without separately authorized data; their initial failures are not claimed as passing. The new integration test uses a minimal synthetic application and does not need internal datasets.

The public integration applies only update routing, maintenance tracking and startup wiring on the existing public baseline, preserving that baseline's public-only options. It intentionally does not overwrite unrelated local curated-resource or model integration changes. Shared update modules, command tools, synthetic tests and public key match the reviewed local delivery; the public-facing instructions replace workstation paths with placeholders. No EXE, private key, private config, database, customer log or internal document is committed.

Current scope: server capability deployed, stable release absent, test channel closed; client update/replacement/restart logic remains the assistant project's responsibility. See `docs/v2/ASSISTANT_UPDATES.md`, the public key and the complete signed test example for integration.
