# 知识单元检索：局部原型与设计边界

状态：本地资料系统待最终验收。原型未接入运行中的 HTTP/专家服务，不代表公网 AI 完成。没有安装 Onyx、RAGFlow、Docling、LlamaIndex 或 Haystack。

## 采用的设计

中心思想：不是搜索最像客户问题的文件，而是搜索最能回答客户问题的原始证据，并能准确回到证据所在的完整文档。

| 借鉴来源 | 小灰机采用的原则 | 现有落点 |
|---|---|---|
| Onyx | 来源身份、元数据、可见范围随内容流转 | engine 的原件哈希、位置、授权预过滤；catalog_metadata 的标题、封面型号、版次和原文依据 |
| RAGFlow / Docling | 按内容结构组织，保存元素顺序及原文定位 | 复用已解析 blocks/locator，原型以核对过的行、主题、步骤范围恢复单元；不重新解析或引入解析模型 |
| LlamaIndex | 细粒度命中后恢复所属父级上下文 | proximity 的候选定位与分页读取；增加单元 ID、父文档 ID、来源片段和完整性标识 |
| Haystack | 多个召回来源组织合流，去重后排序 | 保留 quick-retrieval 已有产品声明、案例、FTS、目录多路组织；本轮不另造召回系统 |

这是结合现有源码的设计选择，不表示这些框架自带的完整功能已落地。

官方参考：[Onyx 来源连接与权限](https://docs.onyx.app/overview/core_features/connectors)、[RAGFlow 按资料形态选择解析方法](https://github.com/infiniflow/ragflow/blob/main/docs/guides/dataset/configuration.md)、[Docling 文档结构与溯源模型](https://github.com/docling-project/docling/blob/main/docs/concepts/docling_document.md)、[LlamaIndex 父子上下文恢复](https://developers.llamaindex.ai/python/framework/integrations/retrievers/auto_merging_retriever/)、[Haystack 多路结果合流](https://docs.haystack.deepset.ai/docs/documentjoiner)。

## 本轮实际实现

- `knowledge_units.py` 是现有 blocks 之上的只读视图，不增加数据库、向量库、模型或 HTTP 路由。输入是本地受信、核对过的来源范围，不接受浏览器任意提交边界。
- 单元保存原件哈希、父文档 ID、来源 block、字符范围、原有页码/工作表/行/列和用途列表。同一单元可有多个用途，不作为排他分类路由。
- 原文片段必须与记录的文本哈希一致；跨原件、跨业务行、跨工作表及部分明确跨案例/型号边界拒绝读取。复杂的隐含边界仍需核对，不能称为已经自动识别。
- 表头只作为来源上下文保留，不与其他客户业务记录合并。Excel 单元格坐标保留；稀疏列、合并单元格及版本列不得按压平后的字符串顺序猜测对应关系。
- 未核对区域只返回实际解析片段并标记不完整；它不能吞回同一 PDF block 中已核对的其他主题。
- `proximity.search/read` 只新增可选内部上下文构造器。默认路径保持原状；原型授权集合在 FTS 候选限制之前生效，文档名筛选只能收窄范围。原型权限集合不是会话 read 授权令牌，未来接入仍须经过既有 expert-evidence 的句柄授权。
- 视频、安装包、固件二进制仅有登记元数据表示，不生成未解析正文。所有目录/正文型号命中仍不证明硬件兼容。

调用链：本地原型调用 → UnitReader.search → proximity.search → engine.query（既有 FTS5/BM25 和约束）→ 命中 block/字符位置 → 已核对单元范围 → 邻近评分 → UnitReader.read → 既有分页读取 → 原始 locator。普通目录浏览和现有专家 HTTP 调用链未切换。

## 对照结果

范围：5 份已解析资料，PDF / DOCX / CSV / XLSX 四种格式、5 个核对过的单元、7 个探索性查询。其中一个真实 FAQ 客户问题分别验证 CSV 与 DOCX 两种原始载体，另外三个为原文派生查询，两个为跨案例负例。不是七个独立客户问题，也不是盲测。

改前使用修改前保存的 proximity 源码，改后使用可选单元视图。每次均约束同名原件；核对五个资料名各仅对应一个内容哈希，避免因目录同名异件造成样本范围差异。每条路径每题运行四次，首次单列，后三次取中位数。

| 指标 | 改前 | 原型 |
|---|---:|---:|
| 两组负例发生跨案例误命中的查询数 | 2 | 0 |
| 五组正例读入邻近无关主题的查询数 | 3 | 0 |
| 五组正例目标单元漏召回数 | 0 | 0 |
| 人工列出的必需证据组成找到数 | 10/14 | 14/14 |
| 七题热运行中位数的中位数 | 77.39 ms | 75.23 ms |

必需组成包括问答列头、工作表版本列与功能行坐标、步骤前提及结果、规格表头/单位/条件。此处是证据组成检查，不是模型答案准确率。速度受本机缓存和样本顺序影响，部分题目变慢，不能宣称加速。

例：DOCX 的同一客户现象与处理结果恢复后，从邻近主题混入的 1794 字符缩至所属案例的 58 字符；PDF 的带载参数保留最大值、推荐值、芯片条件和注意事项，未读入后续其他参数。Excel 读取保留表头和各单元格坐标，不自动给出版本兼容结论；表头原文带有“例”的限定，不能升级成硬件适用证明。

验证：新增单元测试 13/13；既有邻近检索 8/8；授权检索 5/5；专家证据 Node 测试 6/6；三个修改/新增 Python 文件语法检查通过。未跑全套回归。

## 尚未完成及扩展门槛

- 尚未自动生成全库单元，本地样本边界经人工核对；不将样本映射写成型号特例，也不修改产品数据。
- 固件变更说明、培训主题、SDK/API 接口与错误码尚无真实样本验收；类型名称存在不代表对应解析器已实现。不能把 SDK 编译清单当接口定义。
- 现有 PDF 主要是文本偏移，缺可靠表格几何；Excel 合并单元格/继承表头未重建。缺失的结构需以后按来源小批量补足，本轮未重新 OCR、重新扫盘或解析原件。
- 尚无独立保留集的全库误命中/漏命中统计；只有当前核对范围的证据完整度改善，不据此增量扩全库。
- 真实 Bonsai 回答、现场条件适用性判断和多轮自主补查尚未验收，不使用模拟输出替代。
- 后续接入复用 expert-evidence 的搜索后授权读取、quick-retrieval 的多路组织和既有数值/型号/版本校验；不加第二套知识库，也不修改现有有效资料浏览分类。

原始摘录、内部样本映射、客户原问题及完整对照明细只保留本地，不公开。原件、现网、浏览分类和运行服务未改动。
